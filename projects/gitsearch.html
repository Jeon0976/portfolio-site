Case 01 · TMA / Micro Feature

레이어 대신 피처로 나누기 · 피처 하나 = 5타겟

문제

전편은 Domain / Data / Presentation 레이어로 모듈을 나눴습니다. 그래서 검색 기능 하나를 고치려면 세 모듈을 동시에 열어야 했습니다. 전편 README에 적어 둔 한계(모듈이 계속 커지고, 테스트를 잘게 나누기 어려움)가 이 프로젝트의 출발점입니다.

접근

레이어 대신 피처 단위로 모듈을 나눴습니다. 피처 하나를 Interface·구현·Testing·Tests·Demo 다섯 타겟으로 만들면 검색 관련 코드는 FeatureSearch 한 모듈에 모입니다. Clean Architecture를 버린 것은 아닙니다. 피처 안은 그대로 Composition / Domain / Data / Presentation이고, 피처끼리만 Interface로 주고받습니다.

구현

의존 규칙은 빌드 설정으로 막았습니다. 피처끼리는 Interface로만 의존하고 구현체는 App에서만 import할 수 있습니다. FeatureProfile은 FeatureAuth의 Interface만 알기 때문에, 구현 타입을 쓰면 컴파일이 실패합니다.

결과

기능 하나를 고칠 때 여는 모듈이 하나로 줄었습니다. Testing 타겟이 공개한 Mock을 Tests와 Demo가 같이 써서, 피처별로 따로 테스트하고 따로 실행할 수 있습니다.

FeatureProfile/Project.swift 
let project = Project.module(
    name: ModulePaths.Feature.FeatureProfile.rawValue,
    targets: [
        .interface(
            module: .feature(.FeatureProfile),
            dependencies: [.shared(target: .SharedKit)]
        ),
        .implements(
            module: .feature(.FeatureProfile),
            dependencies: [
                .feature(target: .FeatureProfile, type: .interface),
                .shared(target: .SharedKit),
                .core(target: .CoreNetwork),
                .core(target: .CoreDesignSystem),
                // 유일한 피처 간 의존 - Interface에만
                .feature(target: .FeatureAuth, type: .interface)
            ]
        ),
        .testing(/* Stub 공개 */),
        .tests(/* Testing 재사용 */),
        .demo(/* 단독 실행 앱 */)
    ]
)

Case 02 · Tuist / Local Plugin

반복 선언은 플러그인으로, 새 피처는 scaffold 한 줄로

문제

피처 단위로 나누니 타겟이 많아졌습니다. 모듈 8개에 타겟 31개, 피처마다 똑같은 선언이 5개씩 반복됩니다. 스킴까지 손으로 만들면 빠뜨리기 쉽습니다.

접근

반복되는 선언을 Tuist 로컬 플러그인 4개(Environment·Dependency·Configuration·Templates)로 옮겼습니다. 모듈 목록을 enum 한 곳에 모아 두면 워크스페이스가 allCases를 돌기 때문에, 새 피처를 추가해도 기존 모듈은 고칠 것이 없습니다.

구현

피처의 Project.swift에는 .interface / .implements / .testing / .tests / .demo 호출만 남습니다. 스킴은 플러그인이 만듭니다 — 모듈 스킴 8개, 실행 스킴 12개(데모 5개와 본 앱 DEV / PROD). 새 피처는 tuist scaffold 한 줄과 enum 케이스 한 줄이면 됩니다.

결과

DEV 데모는 실제 화면 코드에 Testing 타겟의 가짜 세션만 끼운 것입니다. 서버와 토큰 없이도 페이징과 화면 전환이 실제 코드로 동작합니다.

DependencyPlugin · ModulePaths.swift 
public enum ModulePaths {
    case shared(Shared)
    case core(Core)
    case feature(Feature)
}

// 피처 5타겟의 네이밍 규칙
public enum MicroTargetType: String {
    case interface = "Interface"
    case sources = ""
    case testing = "Testing"
    case unitTest = "Tests"
    case demo = "Demo"
}

public extension ModulePaths {
    enum Feature: String, MicroTargetPathConvertable, CaseIterable {
        case FeatureSearch
        case FeatureAuth
        case FeatureProfile
        // 새 피처 = 케이스 한 줄, 워크스페이스는 allCases 순회
    }
}

Case 03 · CoreNetwork / Interceptor

인터셉터 파이프라인 · 시점과 정책의 분리

문제

토큰을 붙이는 것 같은 공통 처리를 엔드포인트마다 따로 쓰면 중복되고 빠뜨리게 됩니다. 전편은 UseCase가 토큰을 직접 꺼내 넘겨서, 토큰을 쓰는 곳마다 토큰의 존재를 알아야 했습니다.

접근

요청 처리 과정에 훅 두 개를 뒀습니다. adapt는 보내기 직전에 요청을 손보고, retry는 실패한 뒤 다시 보낼지 정합니다. 어느 시점에 끼울지는 프로토콜이, 무엇을 끼울지는 Composition Root의 배열이 정합니다. 실행하는 NetworkSession은 순서만 알고 내용은 모릅니다.

구현

기본 구현은 아무것도 하지 않습니다. adapt는 요청을 그대로 두고 retry는 .doNotRetry라서, 인터셉터는 필요한 훅만 구현하면 됩니다. 요청을 바꾸는 인터셉터와 보기만 하는 모니터(NetworkEventMonitor)는 프로토콜을 따로 뒀습니다.

결과

새 정책은 타입 하나를 만들고 배열에 한 줄 추가하면 됩니다. 프로토콜도 NetworkSession도 고치지 않습니다. 토큰은 AuthTokenInterceptor가 붙이므로 쓰는 쪽은 토큰을 신경 쓰지 않습니다.

RequestInterceptor.swift 
public protocol RequestInterceptor: Sendable {
    func adapt(_ request: URLRequest,
               endpoint: some NetworkEndpoint) throws -> URLRequest
    func retry(_ endpoint: some NetworkEndpoint,
               dueTo error: Error,
               attempt: Int) async -> RetryDecision
}

// 기본 구현 = 아무것도 하지 않음
extension RequestInterceptor {
    public func adapt(...) throws -> URLRequest {
        request        // 항등 - 체인에 끼어도 영향 0
    }
    public func retry(...) async -> RetryDecision {
        .doNotRetry    // 잊어도 사고가 안 나는 방향
    }
}

// NetworkSession.retryDelay - 전원에게 묻되 첫 .retry 채택
for interceptor in interceptors {
    if case .retry(let after) = await interceptor.retry(
        endpoint, dueTo: error, attempt: attempt
    ) { return after }
}
return nil  // 아무도 원하지 않으면 에러 그대로

Case 04 · HTTP / Idempotency

멱등과 재시도 · 안전 검사를 어디에 둘까

문제

네트워크 오류는 다시 보내면 성공할 때가 많습니다. 그런데 POST를 다시 보내면 토큰이 두 번 발급되는 것처럼 같은 작업이 중복 실행될 수 있어, 아무 요청이나 재시도하면 사고가 납니다.

접근

"두 번 보내도 안전한가"는 엔드포인트가 isIdempotent로 선언하고, 다시 보낼지는 인터셉터가 그 값을 보고 정합니다. 따로 선언하지 않으면 RFC 9110대로 HTTP 메서드에서 기본값을 가져옵니다.

구현

재시도는 인터셉터 전체에 물어서 하나라도 .retry면 실행됩니다. 그래서 안전 검사를 별도 인터셉터로 빼면 다른 인터셉터의 .retry에 밀려 무시됩니다. 검사를 재시도 정책 안쪽 첫 guard로 옮긴 이유입니다. 재시도 간격은 지수 백오프로 계산합니다.

결과

다시 보내면 안 되는 요청은 오류 종류를 보기도 전에 재시도 대상에서 빠집니다. OAuth 토큰 교환(POST)은 따로 선언하지 않아도 제외됩니다.

TransientErrorRetryInterceptor.swift 
public struct TransientErrorRetryInterceptor: RequestInterceptor {
    public func retry(
        _ endpoint: some NetworkEndpoint,
        dueTo error: any Error,
        attempt: Int
    ) async -> RetryDecision {
        // 1. 비멱등은 재시도 금지 - 게이트는 정책 안의 첫 guard
        guard endpoint.isIdempotent else { return .doNotRetry }
        // 2. 자체 한도
        guard attempt <= maxRetries else { return .doNotRetry }
        // 3. 일시적 에러만
        guard Self.isTransient(error) else { return .doNotRetry }

        // 지수 백오프: 0.5 -> 1.0 -> 2.0
        return .retry(after: baseDelay * pow(2, Double(attempt - 1)))
    }
}

// NetworkEndpoint.swift - '사실'은 엔드포인트가 선언
public var isIdempotent: Bool {
    switch method {
    case .get, .put, .delete: true
    case .post, .patch: false  // 부수효과 중복 위험
    }
}

Case 05 · Swift Concurrency / Task

ManagedTask · Task 관리 규칙 5가지를 타입으로

문제

UIKit 진입점(viewDidLoad, 버튼 핸들러)은 동기 함수라 async 작업을 시작하려면 Task {}를 써야 합니다. 이 Task를 들고 있지 않으면 화면을 닫아도 요청이 계속 돌고, 늦게 온 예전 응답이 새 화면을 덮어씁니다.

접근

핸들 보관, 재진입 시 취소, deinit 취소, 취소 후 결과 무시, CancellationError 무시. ViewModel마다 지켜야 하는 규칙 5가지인데 컴파일러는 하나도 잡아 주지 않습니다. 매번 복사하는 대신 ManagedTask 타입 하나에 넣었습니다.

구현

replace는 이전 작업을 취소하고 새 작업으로 바꿉니다(검색). runIfIdle은 이미 돌고 있으면 무시합니다(페이징). 슬롯을 비울 때 generation을 비교해 늦게 끝난 예전 작업이 새 작업의 핸들을 지우지 않게 했습니다. 취소는 await 체인을 타고 URLSession까지 내려가 HTTP 요청이 실제로 끊깁니다.

결과

동작 5가지를 테스트로 고정했습니다(전체 24개 중 5개). 호출부마다 있던 [weak self]는 owner 오버로드(replace(with:), sink(with:))로 없애 20곳을 바꿨습니다.

ManagedTask.swift 
@MainActor
public final class ManagedTask {
    private var task: Task<Void, Never>?
    private var generation = 0

    deinit { task?.cancel() }  // 소유자 해제 = 요청 취소

    public func replace(...) {   // 검색: 취소 후 교체
        task?.cancel()
        start(...)
    }
    public func runIfIdle(...) { // 페이징: 진행 중이면 무시
        guard task == nil else { return }
        start(...)
    }

    private func start(...) {
        generation &+= 1
        let startedGeneration = generation
        task = Task { [weak self] in
            do { try await operation() }
            catch is CancellationError { }  // 취소는 침묵
            catch { if !Task.isCancelled { onError?(error) } }
            // 최신 작업일 때만 슬롯 반납 - 늦은 완료가
            // 새 핸들을 지우는 레이스 방지
            if let self, self.generation == startedGeneration {
                self.task = nil
            }
        }
    }
}

Case 06 · ImageIO / Prefetch

아바타 이미지 파이프라인 · 2계층 캐시와 다운샘플

문제

아바타 원본은 목록에 필요한 크기보다 훨씬 큽니다. UIImage(data:)는 이 원본을 그대로 펼쳐서 55pt짜리 자리에 올립니다. 화면에 쓰는 크기의 몇십 배를 메모리에 들고 있는 셈입니다. 셀을 재사용할 때 이전 사람 아바타가 잠깐 보이는 문제도 있었습니다.

접근

캐시를 두 개로 나눴습니다. 내려받은 Data는 디스크에 저장해 같은 이미지를 다시 받지 않게 하고(Data 계층), 셀 크기로 줄인 UIImage는 메모리에 저장해 다시 만들지 않게 합니다(Presentation 계층).

구현

다운샘플러가 ImageIO로 셀 크기만큼만 이미지를 만들어 메모리 캐시에 넣습니다. 이 작업은 메인 스레드 밖에서 합니다. 셀에는 어떤 사용자의 이미지를 기다리는지 representedID로 적어 두고, 이미지가 도착하면 지금 그 셀이 맞는지 확인한 뒤 붙입니다. 화면 밖으로 나간 행은 다운로드를 취소합니다.

결과

스크롤할 때 이미지 처리 때문에 화면이 멈추지 않습니다. 셀을 빠르게 재사용해도 이전 사람의 아바타가 나타나지 않습니다.

ImageDownsampler.swift 
enum ImageDownsampler {
    static func makeImage(
        from data: Data,
        pointSize: CGSize,
        scale: CGFloat
    ) async -> sending UIImage? {
        let maxPixel = max(pointSize.width, pointSize.height) * scale

        let sourceOptions = [kCGImageSourceShouldCache: false] as CFDictionary
        guard let source = CGImageSourceCreateWithData(
            data as CFData, sourceOptions) else { return nil }

        let thumbnailOptions = [
            kCGImageSourceCreateThumbnailFromImageAlways: true,
            kCGImageSourceCreateThumbnailWithTransform: true,  // EXIF 회전 반영
            kCGImageSourceShouldCacheImmediately: true,  // 디코딩을 지금, off-main에서
            kCGImageSourceThumbnailMaxPixelSize: maxPixel  // 셀 크기만큼만
        ] as CFDictionary

        guard let cgImage = CGImageSourceCreateThumbnailAtIndex(
            source, 0, thumbnailOptions) else { return nil }

        // scale 명시 - 165px / 3 = 55pt (스케일 1 가정 버그 방지)
        return UIImage(cgImage: cgImage, scale: scale, orientation: .up)
    }
}
